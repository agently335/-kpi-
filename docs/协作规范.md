# 三人协作 Git 规则

> 不是为了规范而规范，是为了**避免互相覆盖代码**。
> 三个人改同一个文件最容易出事，按这份规则走就不会。

---

## 一、永远不要在 main 上直接改代码

**main 分支是"能跑"的分支。** 任何时候 clone 下来 `python -m uvicorn main:app` 都必须能启动。

所以：

```powershell
# 开始干活前，先切一个自己的分支
git checkout -b 你的名字-w2-任务名

# 例子
git checkout -b jia-w2-upload-page
git checkout -b yi-w2-dataset-api
git checkout -b bing-w2-train-func
```

干完、测过、能跑，再合并回 main。

---

## 二、每天第一次干活前，先同步

```powershell
git checkout main
git pull
```

**不 pull 直接改，是冲突的第一大原因。**

---

## 三、提交信息的写法

格式：`[周次] 做了什么`

```powershell
git commit -m "W2: 实现 POST /datasets 上传与落库"
git commit -m "W2: 训练函数支持随机森林，accuracy 0.89"
git commit -m "W2: 前端上传页调通 /health"
```

**不要写**：`update`、`修改`、`fix`、`111`。三周后你自己都看不懂。

---

## 四、分支怎么合并回 main

**推荐：在 GitHub 上开 Pull Request（PR）**

1. 把分支推上去：`git push -u origin 你的分支名`
2. GitHub 会提示 "Compare & pull request"，点它
3. 填标题和说明，点 Create pull request
4. 让另外一个人看一眼，点 Merge

**为什么走 PR 而不是直接 merge？**
因为 PR 页面能看到"改了哪些行"。如果有人不小心删了别人的代码，一眼就能发现。

**如果只有你一个人改，急着推进，也可以直接：**
```powershell
git checkout main
git merge 你的分支名
git push
```
但**至少每周五合并前让另一个队友看一眼**。

---

## 五、谁负责守 main

**乙是 main 分支守护人。**

职责：
- 每周五检查 main 能正常启动
- 发现 main 坏了，立刻在群里说，优先修
- 合并 PR 前至少点开 diff 看一眼

不是"乙说了算"，是"乙负责确认 main 没坏"。

---

## 六、冲突了怎么办

看到这个提示就是冲突了：

```
CONFLICT (content): Merge conflict in backend/app/config.py
```

**不要慌，不要删文件重来。** 按这个顺序：

1. 打开冲突的文件，会看到这样的标记：
   ```
   <<<<<<< HEAD
   你本地的代码
   =======
   别人提交的代码
   >>>>>>> other-branch
   ```

2. **两个人一起决定保留哪段**（这是必须沟通的时刻，不要自己猜）

3. 改完删掉 `<<<<<<<`、`=======`、`>>>>>>>` 这三行

4. 标记已解决并提交：
   ```powershell
   git add 冲突的文件
   git commit -m "merge: 解决 config.py 冲突，保留字段顺序定义"
   ```

**冲突几乎总是发生在同一个文件同一段。** 想少冲突，就按下面的分工避开。

---

## 七、三个人的文件边界（重要）

按这个分工，冲突率接近零：

| 谁 | 只改这些 | 绝对不改 |
|---|---|---|
| **甲** | `frontend/**` | `backend/**` |
| **乙** | `backend/app/db/**`、`backend/app/routers/**`、`backend/main.py`、`docs/api.md` | `backend/app/services/train.py`、`backend/app/services/predict.py` |
| **丙** | `backend/app/services/train.py`、`backend/app/services/predict.py`、`backend/tests/**` | `backend/app/routers/**`、`frontend/**` |

**三个人都只能改的（要改先说一声）**：
- `backend/app/config.py` —— 里面有冻结的特征顺序
- `backend/app/schemas.py` —— 接口字段定义
- `docs/api.md` —— 接口契约

> 这三个文件改动会影响所有人，**改之前必须在群里说，改完更新 api.md 的变更记录**。

---

## 八、什么不要提交

`.gitignore` 已经挡掉了：

- `__pycache__/`（Python 缓存）
- `*.db`（SQLite 数据库，每个人本地自己生成）
- `*.pkl`、`models/`（训练出的模型文件，太大）
- `uploads/`（上传的临时文件）
- `node_modules/`（npm 依赖）
- `.venv/`

**如果不小心提交了：**
```powershell
git rm --cached 文件名
git commit -m "chore: 移除误提交的生成文件"
```

---

## 九、每天收工前

```powershell
git add -A
git commit -m "W2: 今天做到哪了"
git push
```

**哪怕只写了一半也提交。** 提交到自己的分支不会影响别人，但能防止电脑坏了全丢。

---

## 十、三条救命命令

**想撤销还没提交的修改（回到上次提交的样子）：**
```powershell
git checkout -- 文件名
```
> ⚠️ 会丢失你的修改，确认再说。

**想看看自己改了哪些行：**
```powershell
git diff
```

**彻底搞乱了，想回到干净状态（保留代码，丢弃未提交的改动）：**
```powershell
git stash
```
> 用 `git stash pop` 可以捡回来，不会真丢。

## 附：常用命令速查

```powershell
git status                  # 我现在改了什么
git log --oneline -5        # 最近 5 次提交
git checkout -b 新分支名     # 建分支并切过去
git checkout main           # 切回 main
git pull                    # 拉最新
git add -A                  # 暂存所有改动
git commit -m "说明"        # 提交
git push                    # 推上去
```
